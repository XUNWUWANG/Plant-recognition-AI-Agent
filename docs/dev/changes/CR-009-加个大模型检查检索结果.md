# CR-009 轻量级 Agentic RAG：检索充分性判断与工具重选

> 文件名（大白话）：加一个大模型检查检索结果
> 正式名称：轻量级 Agentic RAG 的检索充分性判断与工具重选机制

- 状态:已批准方向,待实施(用户于 2026-11-25 选择方案 B)
- 日期:2026-11-25
- 依赖:CR-001 ~ CR-008 已完成;**实施前必须先完成 CR-010(公平评测)、CR-011(盲症状集)与 CR-014(预注册规则)**
- 范围变更:定向解除任务书 §2.2 中"LLM 做路由 / LLM-as-judge"的限制
  - 仅允许:LLM 判断"检索证据是否充分" + 选择"换哪种检索工具再查一次"
  - 仍不允许:多轮对话、查询改写、用 LLM 给最终答案打分

## 1. 变更原因

现状是**规则路由 + 单次回退**:规则表决定走 BM25/稠密/混合,质量不足时固定改跑 hybrid。它能工作,但没有"自检"能力,严格意义上不构成 Agentic RAG;在"用户不说植物名、只描述症状"这类查询上,规则也无从判断检索结果是否够用。

目标:在**在线问答(api 路线)**的检索环节加入一次 LLM 决策,形成"检索 → 自检 → 换工具重试"的闭环,使"Agentic RAG"这一表述成立。

## 2. 影响范围

- 新增:`agentic/` 包
  - `decider.py`:LLM 充分性判断与工具选择(严格 JSON,不生成答案)
  - `service.py`:`retrieve_agentic()`,执行首轮检索 → 决策 → 至多重查一次
  - `cache.py`:决策缓存(JSONL,按 query+plant_hint 哈希)
- 修改:`plant/orchestrator.py`(api 路线调用 agentic;local 路线不调用)、`retrieval/rag.py`(新增内部"强制路线"入口,不改公共签名)、`retrieval/settings.py`(开关与阈值)、`retrieval/eval.py`(新增 agentic 评测与回放)、README、任务书、架构说明
- 新增数据:`data/eval/agentic_decisions.jsonl`(录制的大模型决策,用于离线回放评测)
- 新增产物:`指标/retrieval/agentic对比.md`(规则 vs gate vs full 的指标、门控率、调用数、延迟)
- **不动**:CV 链路、识图逻辑、`retrieval` 的检索算法本身、本地路线的零 API 行为

## 3. 方案要点

### 3.1 位置

仅在 **api 问答路径**:第一次检索之后、生成建议之前。local 路线不调用任何 LLM,保持现有规则检索。

### 3.2 何时调用(门控,控制成本)

不是每题都问大模型。满足任一条件才调用 decider:

- 查询里没有植物本名/别名/学名(规则最弱、最需要自检);
- 首轮 Top-1 覆盖度 < 0.6;
- 首轮 Top-1 余弦 < 0.5;
- **首版不启用**"hybrid 且未回退"这一条，避免门控规则过多。

其余情况直接沿用规则结果,避免多一次调用。

> 门控细节:BM25 路线没有 `top1_cos`,跳过余弦条件;只按覆盖度判断。
>
> 在现有 120 题上的实测:门控触发 **32/110(29.1%)**;"无植物名"触发 **0 次**,覆盖度 < 0.6 为 30 次,余弦 < 0.5 约 **6 次**(阈值附近,允许 ±1,以产物为准)。结论:旧题集能触发,但"用户不说植物名"这一核心场景必须靠 CR-011 的盲症状集才能真正验证,不能拿旧题集的触发率代替。

### 3.3 LLM 输入与输出

输入:用户问题、可选植物名、首轮 Top-3 片段(标题 + 前 200 字)、可选路线集合。

输出(严格 JSON,`temperature=0`):
```json
{"sufficient": true, "action": "keep", "reason": "一句话"}
```
- `action` 取值按是否已知植物区分：
  - 已知植物名/`plant_hint`：`{keep, dense, hybrid, bm25}`；
  - 未知植物名：`{keep, hybrid, bm25}`（dense 在无过滤症状上最弱，不允许选）；
- `keep` 表示保留首轮路线与结果；若首轮是 dense，`keep` 即继续用 dense；
- **不允许改写查询**,只允许换检索工具；
- 不生成最终答案,不评价答案质量;
- 超时(默认 8s)、无 Key、JSON 解析失败 → 直接回退到现有规则路由。

### 3.4 重试

`action != keep` 时,用所选路线在同一实体过滤范围内重查一次;**最多一次**。最终片段进入建议生成,沿用现有 `advice.service`。

### 3.5 缓存与回放

- 决策缓存 key = `sha1(query | plant_hint | 首轮 Top-3 chunk_id | kb_hash | model_revision)`;
- 知识库、模型版本、query 或首轮结果变化时,缓存自动失效并需重录;
- 每次真实调用记录:模型名与 revision、时间、原始响应、是否重试;
- 评测时**只读缓存回放**,不调 API,保持"评测零 API + 确定性";
- 录制阶段的 API 成本、耗时与模型版本单独报告,不计入零 API 评测表。

### 3.6 开关与默认值

- `AGENTIC_ENABLED` 默认 **关闭**;评测达标后再默认开启(api 路线);
- local 路线始终关闭;
- 关闭时行为与当前 adaptive 完全一致。

### 3.7 不做

- 多轮对话、记忆;
- 查询改写 / 多跳;
- LLM-as-judge 给最终答案打分;
- cross-encoder 重排;
- 修改识图与 CV 链路。

## 4. 评测计划

### 4.1 对照组

在现有 5 组之外**单独**增加 `agentic`,不改动原 5 组的可比性:

| 组 | 说明 |
|---|---|
| dense+filter | **主基线**:P1 下三项最高(0.700 / 0.950 / 0.836) |
| hybrid+filter | 次强基线(0.682 / 0.932 / 0.824) |
| adaptive(规则) | 现有产品路径(0.655 / 0.927 / 0.804) |
| agentic-gate | 仅 LLM 判断充分性,不换路 |
| agentic-full | LLM 判断 + 至多换路一次 |

> 基线选择说明:adaptive 的增益主要来自实体过滤;过滤后 dense+filter 才是最强基线,hybrid+filter 是次强基线。验收必须同时看这两个基线。
> 括号内顺序:Top-1 / Recall@5 / MRR。P1 实测中 dense+filter 的中位延迟也不高于 adaptive;agentic 必须证明额外调用带来超过它的收益,否则默认关闭。

### 4.2 题集

- 现有 120 条保持不变;
- 新增 **60 条无植物名盲症状题**(CR-011;红级范围变更已批准),另设 30 条 unanswerable 扩展,单独报告;
- 盲题结论按 CR-014 预注册规则判定。

### 4.3 指标

- Recall@5、MRR、Top-1 命中率(三者分开报);
- 路由分布、门控触发率、重试率;
- 分路线延迟(median/P95/mean,固定 dtype 与线程数)与相对最强基线的实际节省;
- 额外 LLM 调用次数、额外延迟、录制阶段 API 成本;
- 阈值敏感性沿用 CR-012 的表,不另起一套;
- 所有组使用**相同实体过滤协议**,不允许只有 agentic 过滤。

### 4.4 验收线

- 盲症状子集(CR-011):`agentic-full` 的 Recall@5 比 **最强盲题基线 ≥ +0.05**;同时比 adaptive ≥ +0.05;
- 全量 110 道可答题(120 扣除 10 条 unanswerable):不得低于 **dense+filter 1 个百分点**以上,也不得低于 hybrid+filter 与 adaptive;
- 若达不到:默认保持关闭,记录为"尝试过但无收益",不进入论文主结论。

## 5. 风险

| 风险 | 应对 |
|---|---|
| 每题多一次 LLM 调用,延迟上升 | 门控只在弱信号时调用;报告额外延迟与触发率 |
| LLM 决策不稳定 | temperature=0;录制 + 回放;记录模型版本 |
| 无 API Key 时无法评测 | 先录制一次,再离线回放;测试只测解析与回退逻辑 |
| 规则基线已经很强,增益不足 | 验收线卡死;无收益则默认关闭,不硬吹 |
| 论文"零 API 评测"被破坏 | 打分阶段零 API,仅录制阶段用 API,并单独注明 |
