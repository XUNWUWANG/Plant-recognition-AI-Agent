## 1. 变更原因

原任务书同时承担需求契约、实现规格、验收清单和历史记录,并把大量实现细节写成"锁定决策/不得更改/扁平模块"。这导致后续合理的结构调整(CR-003~007)反复与文档冲突;部分条款已过时(如 50 条临时查询、扁平模块),部分条款把"不做产品功能"和"不做工程优化"混在一起。

## 2. 影响范围

- 重写:`docs/dev/任务书.md` → 只保留契约层
- 新增:`docs/dev/架构说明.md` → 承载实现层
- 更新:`docs/dev/变更记录.md`(文档分工、索引)
- 微调:`CR-001`、`CR-002`、`CR-003`、`CR-006`、`CR-007` 的交叉引用
- **不动**:任何 `.py`、配置、数据、评测产物

## 3. 方案要点

### 3.1 三层文档

- 契约层(任务书):目标、范围、数据/检索/评测契约、验收、手工场景;
- 实现层(架构说明):目录、模块、接口、依赖方向、缓存生命周期、CLI、技术债;
- 记录层(变更记录 + changes/):每个 CR 的原因、影响、验收、回滚。

### 3.2 约束三色

- 🔴 红:目标、产品范围、评测集定义、指标公式、验收标准、不做清单;
- 🟡 黄:目录/包结构、文件名、CLI、依赖、内部算法、阈值、默认模型;
- 🟢 绿:注释、格式、私有函数拆分、无行为重构。

### 3.3 关键条款变更

| 原条款 | 新条款 |
|---|---|
| "保持仓库现有风格:扁平模块" | 删除;模块边界清晰即可,结构调整走 CR |
| "不改 train.py/compare.py" 作为绝对禁令 | 默认不改;例外由 CR 批准并复跑/说明 CV 结果 |
| 10 条"锁定决策不得更改" | 拆成红(研究结论)与黄(工程实现)两级 |
| "唯一事实来源:本文件" | 需求/验收以任务书为准;实现以架构说明与已批准 CR 为准 |
| §14 实现备注 | 压缩为"历史里程碑",细节留在 CR-001/002 与架构说明 |
| M0 必须 50 条查询 | 标注为历史过程,不再约束后续 |
| §4 逐文件规格 | 迁入架构说明,按实际代码描述 |

### 3.4 变更授权

- 黄色约束的调整:立 CR → 批准 → 实施 → 测试与五组指标回归 → 更新架构说明与索引;
- 红色约束的调整:必须由用户明确批准,并在任务书版本说明中记录;
- 绿色改动可直接做,但测试必须绿。
