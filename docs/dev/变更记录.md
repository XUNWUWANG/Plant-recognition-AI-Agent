# 变更记录与变更流程

> 本文件有两个用途:
> ① 约定以后怎么改(变更驱动 / 契约驱动);
> ② 记录已经发生的变更(按 CR 编号追加)。
>
> 事实来源分三层:需求与验收 → `docs/dev/任务书.md`;实现结构与接口 → `docs/dev/架构说明.md`;变更过程 → 本文件与 `changes/`。本文件只回答"改了什么、为什么改、影响谁、怎么验收",不复制任务书里的完整规格。

---

## 一、核心结论

后续修改**不需要重写整份任务书**,但必须**增量更新契约文档**:

1. 不从零重写全局任务书。
2. 每有新需求或改动旧逻辑,先建一份轻量变更提案 `CR-xxx`,说明:变更原因、影响范围、验收标准。
3. 修改完成后:验收口径变化回写任务书;实现细节变化回写架构说明;两者都无变化则只更新 CR 与索引。
4. **铁律:先改文档,后改代码。** 不要让 AI 在没有文档约束的情况下直接改代码,否则容易偏离既有架构。

---

## 二、文档分工

| 文档 | 角色 | 更新时机 |
|---|---|---|
| `docs/dev/任务书.md` | 需求与验收契约:范围、指标、验收 | 仅范围/验收变化时 |
| `docs/dev/变更记录.md`(本文件) | 变更流程 + 变更索引 | 每次变更 |
| `docs/dev/changes/CR-xxx-*.md` | 单个变更提案/记录 | 每个变更一份 |
| `docs/dev/架构说明.md` | 目录、模块、接口、依赖方向、CLI | 结构/接口变化时 |
| `README.md` | 对外使用入口:安装、运行、评测 | 命令/入口变化时 |
| `docs/thesis/开题设计方案（给老师）.md`、`docs/thesis/毕设说明.md`、`docs/thesis/参考文献.md` | 论文与答辩材料,不参与实现 | 写作时 |
| `docs/thesis/实验素材清单.md` | 论文数字、表格、截图登记 | 每个 CR 完成后 |
| `git log` | 客观事实记录:谁在何时改了哪些行 | 每次提交 |

不要为"每次对话"单独建日志:git 才是权威记录。人工日志只按 CR/里程碑写。

## 四、docs 目录约定

按"是否约束实现"分两类(已于 2026-11-25 完成迁移):

```text
docs/
├── dev/                        # 开发契约类
│   ├── 任务书.md
│   ├── 变更记录.md
│   ├── 架构说明.md             # 实现层
│   └── changes/
│       ├── _模板.md
│       └── CR-001-重做找资料功能.md
└── thesis/                     # 论文/答辩材料

    ├── 毕设说明.md
    └── 参考文献.md
```

约定:
- 写代码/验收前只看 `dev/`;`thesis/` 只用于写作汇报,不参与实现;
- 新增变更提案放 `dev/changes/`,并在下方"变更索引"追加一行;
- 移动文档时用 `git mv` 保留历史,并同步更新文内路径引用。

## 六、git 记录约定

- 粒度:**一个里程碑 / 一个可验收功能 / 一个缺陷修复 = 一个 commit**;不按对话提交。
- 提交前跑测试;不提交半坏状态。
- 提交信息写"为什么",例如:
  - `feat(retrieval): 增加 BM25/向量/RRF 三路检索`
  - `fix(router): 修正别名查询误判为本名`
  - `docs: 补充 CR-001 检索子系统变更记录`
- 里程碑可打 tag(`m0-gate`、`m1-hybrid`),方便回到某个阶段。
- 需要时间线时用:
  ```bash
  git log --oneline --date=short --pretty=format:"%ad %h %s"
  git log --stat
  ```
