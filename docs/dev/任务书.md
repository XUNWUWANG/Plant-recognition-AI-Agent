## 1. 背景与目标

### 1.1 现状（已核实）
- 项目：DeepSeek 视觉识别（API）+ 本地 MobileNetV3-small（CV）+ 知识库检索（RAG）+ LLM 生成养护建议 + Gradio 界面。
- 检索只有一条路：**子串字面匹配**（`rag._score`：名字命中 +5，`token in text` +1）。
- **检索查询永远是"识别出的植物名"**：`app.py:87-88` → `tools.plant_advice(r1["name"])` → `rag.retrieve(plant_name)`；界面**没有自由文本输入**。
- 知识库只有 **1 个文件、23 条、3309 字**，基本每植物一整段。
- 结论：当前基线的"名字查询"召回≈100%，**没有可提升空间**；必须先加问答入口 + 分块扩库。

### 1.2 目标（本次要做完的）
1. 增加**自由文本提问**入口（可纯文字，可"照片 + 追问"）。
2. 知识库**多主题分块**（约 130-160 chunks）。
3. 实现 **BM25 + 向量（Qwen3-Embedding-0.6B）+ RRF** 三路检索。
4. 实现**特征路由 + 检索质量回退纠错**（CRAG 简化）。
5. 建立 **120 条标注评测集** 与 **5 组对照实验**，输出表格与误差分析。
6. 全流程**可复现、评测零 API**。

### 1.3 非目标
见 §12。

**决策表（精确实现）**：

| 条件（按顺序判断） | 返回 |
|---|---|

**chunk 构建规则**：
- 按 `^## (.+)$` 切植物，按 `^### (.+)$` 切小节；无 `###` 的植物整段作为 `section="正文"`。
- `chunk_id = f"{plant}#{section}"`；重复小节追加 `#2`、`#3`。
- 丢弃 `< CHUNK_MIN_LEN` 的片段。
- 解析别名：`别名/学名：` 行、`### 别名` 小节；分隔符 `、,，;；/`。
- 去重：同名植物只保留第一条（当前 kb 有重复"龟背竹"）。

**检索执行流程（`retrieve` / `retrieve_debug` 共用）**：
1. `_ensure_indexes()`。
2. 若 `not query.strip() and not plant_hint` → 返回 `[]`。
3. `q = query.strip() or plant_hint`。
4. `route = router.decide(q, plant_hint, _names)`。
5. 执行：
   - `bm25` → `_bm25.search(q, FUSE_TOP_N)`
   - `dense` → `_dense.search(q, FUSE_TOP_N)`；记录 `top1_cos`
   - `hybrid` → `rrf_fuse([bm25_top10, dense_top10], RRF_K, TOP_K)`
6. 若 `route != hybrid`：`new_route = router.should_retry(route, top1_text, q, top1_cos)`；非空则**改跑 hybrid**，`retried=True`。
7. 截取 `topk`，格式化为 `## {plant} · {section}\n{text}`。
8. 计时仅包裹第 5-7 步（不含首次构建）。

**向后兼容**：原调用 `rag.retrieve("绿萝")` 必须仍可用（query 非空、plant_hint=None → 决策表命中 BM25）。

- `naive` 与其余 4 组使用**同一份 chunks**。
- `adaptive` 调 `rag.retrieve_debug`；其余组直接调对应检索器（不走路由）。
- 每组先做一次 warm-up（不计时），再正式计时。
- 评测过程**禁止调用任何 LLM API**。
- 结果确定性：无随机、无采样。

## 5. 数据设计（精确 schema）

### 5.1 KnowledgeChunk（`models/chunks.json`）

```json
{
  "kb_hash": "sha1...",
  "chunks": [
    {"id": "绿萝#光照", "plant": "绿萝", "section": "光照",
     "text": "绿萝喜散射光……", "source": "植物养护手册.txt",
     "aliases": ["黄金葛", "魔鬼藤", "Epipremnum aureum"]}
  ]
}
```

### 5.2 EvalCase（`data/eval_queries.jsonl`）

```json
{"id":"q001","query":"绿萝叶子发黄是怎么回事","type":"symptom",
 "plant_hint":"绿萝","relevant":["绿萝#常见问题","绿萝#浇水"],
 "difficulty":"easy","note":"用户口语问法"}
```

- `type ∈ {entity, symptom, alias, multi, unanswerable}`
- 规模：entity 30、symptom 40、alias 25、multi 15、unanswerable 10（共 120）。
- `relevant` 为 chunk_id 列表；`unanswerable` 的 `relevant` 为 `[]`。
- 规则：query 不得直接照抄 chunk 原文超过 8 个连续字；`alias` 题的 query 使用别名/学名而非本名。

### 5.3 向量缓存（`models/emb_qwen3_0.6b.npz`）

```
emb:     float32 [N, d]
ids:     str [N]
kb_hash: str
model:   str
```

加载时校验 `kb_hash` 与当前 chunks 一致，否则重建。

## 6. 指标定义（精确公式）

设题目 `q` 的相关集合 `R(q)`，检索 Top-5 为 `T5(q)`。

- **Recall@5** = `|R(q) ∩ T5(q)| / |R(q)|`（`R(q)` 为空时不计入）。
- **MRR** = `mean(1 / rank(first_relevant))`（未命中记 0；仅统计 `R(q)` 非空）。
- **延迟**：包裹单次检索（不含首次构建/模型加载）；报告中位数与 P95。
- **路由准确率**（自动计算，无需人工标最优路线）：
  `route_ok(q) = 1 if Recall5_adaptive(q) ≥ max_{config} Recall5_config(q) - 1e-9 else 0`，再取平均。
- **分层**：按 `type` 分别报告 Recall@5 与 MRR。
- **库外问题**：不进入 Recall/MRR；报告 `平均 Top-1 覆盖度` 与 `平均 Top-1 余弦`，用于说明"系统对库外问题的置信度是否更低"。

## 8. 施工顺序与闸门

### M0 判据闸门（0.5-1 天）——**不通过就停**
1. 完成 kb 分块（§4.2）与 `chunks.json`。
2. 生成 50 条临时查询（`scripts/build_eval.py` 候选 + 人工改写 50 条即可）。
3. 只跑 `python eval_retrieval.py --configs bm25,dense`。
4. **通过条件**（满足任一）：
   - BM25 与 Dense 的 Recall@5 差距 ≥ 0.10；或
   - 两路错误集合存在明显互补（至少 15% 的题目"一路错另一路对"）。
5. 不通过 → 停止，输出 `指标/M0_判据.md`：两路 Recall、互补题数、失败类型分布、扩库/改查询建议。

### M1 检索层（2-3 天）
- `retrievers.py` + `rag` 的 BM25/Dense/RRF 跑通。
- 产出 naive/bm25/dense/hybrid 4 组指标。
- 验收：hybrid Recall@5 ≥ 单路最好值（允许 ±0.02 波动）。

### M2 路由层（2-3 天）
- `router.py` + `rag.retrieve` 路由与回退。
- 产出 adaptive 第 5 组。
- 验收：adaptive Recall@5 ≥ hybrid − 0.02，且中位延迟 ≤ hybrid × 1.1。

### M3 接入产品（3-4 天）
- `tools/agent/app` 改造；纯文字、纯图片、图文 三种输入可用。
- 完成 120 条评测集人工改写与校验。
- 验收：4 个手工场景通过（见 §10）。

### M4 评测与交付（3-5 天）
- `eval_retrieval.py` 全套输出 + SQLite 日志 + 误差分析。
- README 更新。
- 验收：§9 全部通过。
