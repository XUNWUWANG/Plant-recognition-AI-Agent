## 1. 背景与目标

系统面向植物养护场景:用户上传植物照片、输入养护问题,或两者同时提供;系统识别植物,检索本地知识库,生成养护建议;若为花卉,附带花语。

一期目标(已完成并持续维护):

1. 支持纯文字、纯图片、图片+追问三种输入;
2. 本地知识库分块检索(BM25 + 稠密向量 + RRF);
3. 查询特征路由与检索质量回退;
4. 120 条主评测集、五组基线 + 公平消融/盲测扩展(规划),全程可复现、评测打分零 API;
5. 本地模型路线全程离线、零 API 额度。

## 2. 范围

### 2.1 必须完成

- 三种输入路径可用,`api` 与 `local` 两条路线语义正确;
- 检索支持植物名、别名、学名、症状口语问法;
- 库外问题给出明确提示,不强行返回无关内容;
- 评测可离线运行,产出对比表、错误案例与 SQLite 日志;
- 单元测试覆盖分块、RRF、路由、兼容性。

### 2.2 产品范围外(红)

- 多轮对话记忆 / 会话状态;
- 多跳检索、查询改写(query rewriting);
- 用 LLM 做通用路由或给最终答案打分
  (经 CR-009 批准、仅限"检索充分性判断 + 重选一次检索工具"的轻量 Agentic RAG 除外;可选工具见 CR-009 §3.3);
- LangChain / LangGraph 等框架;
- cross-encoder 重排;
- 训练或微调 CV/LLM 模型;
- 用其他 Web 框架替换 Gradio;
- 把知识库扩到 23 种以上植物。

以上为论文范围决策,不在代码优化中顺手扩展。

### 2.3 工程默认(黄)

- 不修改 CV 训练/对比脚本与权重文件,例外见 §0.5;
- 目录与包结构、CLI、依赖、内部算法可随 CR 调整;
- 新增依赖必须写进 `requirements.txt` 并说明用途。

## 3. 功能契约

| 输入 | 识别 | 建议 | API 调用 |
|---|---|---|---|
| 纯文字 | 不识别 | 检索 + 生成建议 | `api`:1 次;`local`:0 次 |
| 纯图片 | 识别植物 | 生成建议 | `api`:识图 1 次 + 建议 1 次;`local`:0 次 |
| 图片+追问 | 识别植物 | 结合问题检索/生成 | 同上 |

- `local` 路线:识别与建议全程本地,不调用任何 API;
- `api` 路线带图时为两次模型调用(识图 + 建议),纯文字为一次;CR-009 启用且门控命中时,额外增加 1 次“检索决策”调用;
- 视图中无图片且无问题时,返回"请上传植物照片,或输入一个问题。";
- 知识库未命中或相关性不足时,走 `generic` 提示,不输出无关条目;
- 向后兼容:`rag.retrieve("绿萝")`、`tools.plant_advice_offline("绿萝")` 仍可用(转发壳见 CR-006)。

## 4. 数据契约

### 4.1 知识库

- 位置:`kb/植物养护手册.txt`(可多文件);
- 结构:`## 植物名` + `### 小节`(特征/光照/浇水/温度/施肥/病虫害/常见问题);
- 规模:20 种植物 × 7 小节,约 130–160 chunks;
- `### 特征` 必须包含 `别名/学名:` 行,供别名检索。

### 4.2 KnowledgeChunk

```json
{"id": "绿萝#光照", "plant": "绿萝", "section": "光照",
 "text": "……", "source": "植物养护手册.txt", "aliases": ["黄金葛", "Epipremnum aureum"]}
```

### 4.3 EvalCase

```json
{"id": "q001", "query": "绿萝叶子发黄是怎么回事", "type": "symptom",
 "plant_hint": "绿萝", "relevant": ["绿萝#常见问题", "绿萝#浇水"],
 "difficulty": "easy", "note": "用户口语问法"}
```

- `type ∈ {entity, symptom, alias, multi, unanswerable}`;
- 主评测集固定 120 条:30 / 40 / 25 / 15 / 10;
- `unanswerable` 的 `relevant` 为空;
- query 不得照抄 chunk 原文超过 8 个连续字。
- 盲症状扩展集(CR-011):60–100 条(建议 60)不含植物名/别名的题,单独报告,不并入 120 条主表;另设 unanswerable 扩展 30 条。建集与评测分两段,评测前须冻结 CR-014。

### 4.4 缓存

- `models/cache/chunks.json`:`kb_hash` + chunks,知识库变化时重建;
- `models/cache/emb_qwen3_0.6b.npz`:`emb`、`ids`、`kb_hash`、`model`,hash 或模型不一致时重建。

> CR-005 已完成,缓存位于 `models/cache/`。

## 5. 检索契约

### 5.1 五组配置与公平消融

| 配置 | 定义 |
|---|---|
| naive | 原字面匹配(名字 +5、词元 +1)作用于 chunk |
| bm25 | `rank_bm25.BM25Okapi`(k1=1.5,b=0.75)+ jieba + 汉字级补偿 |
| dense | Qwen3-Embedding-0.6B,失败回退 bge-small-zh-v1.5 |
| hybrid | BM25 与 Dense 各取 Top-10,RRF(k=60)融合后取 Top-5 |
| adaptive | 路由 + 回退 + 实体约束 + 库外闸门 |

公平消融组(CR-010):`bm25+filter`、`hybrid+filter`、`dense+filter`、`adaptive−filter`、`adaptive−retry`。
评测分两套协议:P1 所有组统一实体过滤(主表);P2 保留原五组行为(naive/bm25/dense/hybrid 不过滤;adaptive 为产品路径,自动实体过滤,表内注明)。纯无过滤消融看 P1 的 `adaptive−filter`;禁止只给某一组开过滤。
P1 下当前最强基线为 `dense+filter`(Top-1 / Recall@5 / MRR = 0.700 / 0.950 / 0.836),`hybrid+filter` 次之;所有比较以“最强基线”为准;`dense+filter` 的中位延迟也低于 hybrid/adaptive,最终延迟以 CR-012 固定口径为准。

### 5.2 路由决策(行为契约)

按顺序判断,`plant_hint` 非空视为"含本名":

1. 空查询且有 `plant_hint` → BM25;
2. 含本名/`plant_hint` 且有症状词 → hybrid;
3. 含本名/`plant_hint`、无症状词 → BM25;
4. 只含别名/学名 → hybrid;
5. 只含症状词 → dense;
6. 其他 → hybrid。

> 规则 5(纯症状 → dense)的合理性由 CR-011 盲题验证;无过滤的 dense 在 symptom 上为 0.438,低于 bm25/hybrid。若盲题结果劣于“盲题最佳无过滤基线”(bm25/dense/hybrid 中最高者),按 CR-014 预注册规则调整,不得看完结果临时改规则。

### 5.3 回退与纠错

- BM25:Top-1 覆盖度 < 0.5 → 改跑 hybrid;
- Dense:Top-1 余弦 < 0.4 → 改跑 hybrid;
- hybrid 不再回退。

### 5.4 实体约束与库外闸门

- 查询或识别结果含植物本名/别名/学名时,只在该植物的小节内排序(仅产品路径与 adaptive);
- 评测时过滤协议必须明确标注(CR-010):P1 全过滤;P2 原五组行为(adaptive 含自动过滤,表内注明);
- Top-1 覆盖度 ≥ 0.5 或余弦 ≥ 0.55 视为命中,否则走 `generic`。

## 6. 评测契约

设题目 `q` 的相关集合 `R(q)`,Top-5 为 `T5(q)`:

- **Top-1 命中率** = Top-1 是否在 `R(q)` 内;
- **Recall@5** = `|R(q) ∩ T5(q)| / |R(q)|`(`R(q)` 为空不计);
- **MRR** = `mean(1 / rank(first_relevant))`,未命中记 0;
- 以上三项必须同时报告,不得只报 Recall;
- **延迟**:分路线报告 median / P95 / mean,并给出相对"始终 hybrid+filter"和"始终 dense+filter"的节省;
- **路由效用**:逐题比较 adaptive 与 P1 最强基线 `dense+filter` 的差值,并同时报告 `hybrid+filter` 的差值;报告均值、中位数与胜/平/负;原"达标率"仅作辅助;
- **分层**:按 `type` 分别报告;
- **库外问题**:报告误接收率(被当成有答案的比例)与正常题误拒率;
- **阈值敏感性**:覆盖率、余弦、闸门阈值各扫描至少 3 档(CR-012);
- **不确定性与预注册**:比例指标附 Wilson 95% 区间,配置比较用配对方法;产品决策按点估计,区间仅作参考;盲题结论必须按 CR-014 预注册规则判定;
- **盲症状扩展集**(CR-011):60–100 条(建议 60),单独报告,不并入 120 条主表。

评测协议:

- 五组基线 + 公平消融组使用同一份 chunks;
- 分两套协议:P1 所有组统一实体过滤(主表);P2 保留原五组行为(adaptive 含自动过滤,表内注明);
- 每组先 warm-up,不计时;
- 打分阶段不调用 LLM API;agentic 评测使用"录制 + 回放"(CR-009),录制成本单独报告;
- 无随机、无采样,两次运行结果一致;
- 产物:`指标/retrieval/检索对比表.md`、`指标/retrieval/检索错误案例.md`、`指标/retrieval/eval.db`。

## 7. 验收标准(Definition of Done)

**功能**

- [ ] `python app.py` 启动;纯文字、纯图片、图片+追问均能出结果;
- [ ] `local` 路线全程零 API;`api` 路线调用次数符合 §3;
- [ ] 库外问题给出提示,不崩溃;
- [ ] `rag.retrieve("绿萝")`、`tools.plant_advice_offline("绿萝")` 仍可用。

**评测**

- [ ] `python -m retrieval.eval` 无报错,生成主表与消融表,打分阶段无需 API Key;
- [ ] 输出对比表、错误案例、`eval.db`;
- [ ] P1 公平主表含 `dense+filter`、`hybrid+filter`、`bm25+filter`、`adaptive−filter`、`adaptive−retry`;P2 原五组保留(adaptive 含自动过滤,表内注明);
- [ ] 盲症状扩展集(CR-011,60 条)在 CR-014 冻结后评测,单独报告,并按其预注册规则给出结论;
- [ ] 表内同时含 Top-1、Recall@5、MRR、分类型结果、路由分布、分路线延迟;
- [ ] 比例指标附 Wilson 95% 置信区间,配置比较给出配对差值;
- [ ] 错误案例包含全部 Top-1 错误并分类;
- [ ] 阈值敏感性表与库外误接收/误拒率;
- [ ] agentic(若实施)使用录制 + 回放,打分阶段零 API。

**测试**

- [ ] `python -m unittest discover -s tests` 全绿(当前 16 个用例);
- [ ] 覆盖:chunk 解析、RRF 排序、路由决策表、覆盖率函数、`retrieve` 兼容性。

**质量**

- [ ] 同一输入两次运行结果一致;
- [ ] 向量缓存命中时不重新编码;
- [ ] Windows 控制台无编码错误;
- [ ] 手工场景 1/2/6 有真实图片与截图证据,或明确标注阻塞。

## 9. 风险与回滚

| 风险 | 应对 |
|---|---|
| HuggingFace 下载失败 | 设 `HF_ENDPOINT=https://hf-mirror.com`;缓存后可用 `HF_HUB_OFFLINE=1` |
| 依赖版本冲突 | 记录实测组合,sentence-transformers 失败时 transformers 直载兜底;钉版本由 CR-013 接手 |
| CPU 编码慢 | 缓存 npz;warm-up 后计时;必要时换 bge-small |
| Windows 控制台 GBK | 脚本统一 `sys.stdout.reconfigure(encoding="utf-8")` |
| 知识库重复/空小节 | 去重、`CHUNK_MIN_LEN` 过滤、`--stats` 检查 |
| 重构破坏行为 | 每个 CR 单独提交;测试 + 主表指标必须回归;`naive_retrieve` 可作降级 |
| CV 结果被破坏 | 默认不改 CV 脚本;例外走 CR 并复跑对比 |
