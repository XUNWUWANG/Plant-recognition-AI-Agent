## 一、这个毕设到底做了什么（改造前后对比）

| 维度 | 改造前（GitHub 仓库现状） | 改造后（你的毕设成果） |
|---|---|---|
| 输入 | 只能上传照片 | 照片 **或** 自由文本问题，可「照片 + 追问」 |
| 检索对象 | 23 段、每植物一整段 | 多主题分块（光照/浇水/温度/施肥/病虫害/常见问题），约 130-160 个 chunk |

| 检索决策 | 无，一条路走到底 | 特征路由：点名型走 BM25、症状型走向量、混合型走融合 |
| 出错处理 | 搜不到就搜不到 | 检索质量评估 + 回退换路（CRAG 简化版） |
| 评测 | 只有 CV 的 Top-1/Top-3 准确率 | 检索指标 Recall@5 / MRR / 路由准确率 / 延迟，5 组对照 |

| 成本 | 生成调一次 DeepSeek | 不变；检索全本地，评测零 API |

## 二、你"设计"了什么（重点：老师最看重这个）

老师的原话精神是："这是**设计**，不是写代码"——他拿图书管理系统举例时强调"要设计好数据库"。所以汇报时**不能**说"我改了 rag.py 那 51 行"，而要把工作讲成一套**系统设计**。下面每一小节都是可以直接搬到 PPT / 论文里的一页。

### 2.1 系统设计：分层与解耦

```
┌─────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│ 输入层       │   │ 检索层        │   │ 决策层        │   │ 生成层        │
│ 图片/文本    │──▶│ BM25 / 向量   │──▶│ 路由 + 回退   │──▶│ LLM 组织答案  │
│ (CV 已完成)  │   │ 索引与融合    │   │ 决策与纠错    │   │ (调 API)      │
└─────────────┘   └──────────────┘   └──────────────┘   └──────────────┘
        ▲                                                      │
        └────────────────── 评测层（离线，零 API）─────────────┘
```

- **设计理由**：识图不碰检索、检索不碰生成、生成不碰评测；每层有稳定接口，**可替换、可单独评测、可回退**。
- 答辩点：为什么这样分层？——因为"能单独评测"是研究的前提；如果搅在一起，任何提升都说不清是谁贡献的。

### 2.2 数据设计（对应老师说的"数据库设计"）

这是你回应"设计"二字最有力的部分。你虽然没有用 MySQL，但**设计要素一样不少**：

**概念模型（ER）**

```
Plant 1 ──── N KnowledgeChunk
EvalCase N ──── N KnowledgeChunk   (通过相关性带 grade)
EvalCase 1 ──── N RouteTrace
EvalRun 1 ──── N CaseResult
```

**逻辑设计（表结构）**

| 表 | 字段 | 说明 |
|---|---|---|
| `knowledge_chunk` | `chunk_id`(PK), plant, section, text, source, updated_at | 知识片段主表 |
| `eval_case` | `case_id`(PK), query, type, difficulty, plant_hint | 评测样本 |
| `eval_relevance` | `case_id`(FK), `chunk_id`(FK), grade | 多对多相关度 |
| `route_trace` | `trace_id`(PK), case_id(FK), route, retried, top1_score, latency_ms | 每次检索决策轨迹 |
| `eval_run` | `run_id`(PK), config, recall5, mrr, latency_med, latency_p95 | 一次实验汇总 |

**物理设计（实际落地）**
- 知识库：`kb/植物养护手册.txt`（人工维护的"主数据"）→ 解析为 `models/chunks.json`（"物化视图"）
- 关键词索引：jieba 分词 + BM25 倒排（内存结构）
- 向量索引：`models/emb_qwen3_0.6b.npz`（chunk 向量矩阵 + 内容哈希）
- 评测日志：`指标/eval.db`（SQLite，三张表存运行、逐题结果、路由轨迹）

**一致性 / 失效设计**（老师爱问"数据改了怎么办"）
- 对知识库内容做哈希；哈希变化 → 自动重建 chunks 与向量缓存。
- 主数据（kb）与派生数据（chunks/向量）分离，派生数据可随时重建。

> 讲给老师的一句话：
> "我没有用数据库管理系统，但做了**等价的数据设计**：实体、主键、外键、索引、缓存与失效策略齐全；评测日志落在 SQLite 里，可以直接查'哪种问题路由错了'。"

### 2.3 接口设计（契约）

| 接口 | 契约 | 设计意图 |
|---|---|---|
| `retrieve(query, topk, plant_hint)` | 返回 `list[str]`，格式 `## 植物 · 小节\n正文` | 下游无感；保留旧调用兼容 |
| `router.decide(query, plant_hint, names)` | 返回 `bm25 / dense / hybrid` | 纯函数，可单测、可解释 |
| `router.should_retry(route, ...)` | 返回新路线或 `None` | 纠错机制的唯一入口 |
| `eval_retrieval.run(configs)` | 输出表 + SQLite 日志 | 可复现、可对比 |

- 答辩点：**接口不变更比实现更重要**——所以 `plant_advice_offline`、`agent_handle` 的调用方几乎不用改。

### 2.4 算法设计

- **BM25**：`k1=1.5, b=0.75`；jieba 分词；解决"字面包含"过严的问题，并对词频饱和建模。
- **向量检索**：Qwen3-Embedding-0.6B；**查询加 instruction、文档不加**；L2 归一化后点积即余弦。
- **RRF 融合**：`score = Σ 1/(k + rank)`，`k=60`；只用排名不用分数，避免两路分数尺度不同。
- **路由决策表**（核心设计产物）：

| 查询特征 | 路线 | 理由 |
|---|---|---|
| 空问题 + 有植物名 | BM25 | 名字是精确词 |
| 含植物名/别名 + 无症状词 | BM25 | 精确匹配最稳 |
| 含植物名 + 症状词 | 混合 | 既要锁定植物，又要理解症状 |
| 只含别名/学名 | 混合 | 别名精确 + 语义兜底 |
| 只含症状/意图词 | 向量 | 口语与文档用词不一致 |
| 其他 | 混合 | 保守策略 |

- **回退纠错**（CRAG 简化）：
  - BM25 → 计算查询词在 Top-1 片段中的**覆盖率**，< 0.5 则改走混合；
  - 向量 → Top-1 余弦 < 0.4 则改走混合；
  - 混合 → 不再回退（避免循环）。

### 2.5 实验设计（很多本科生没有这一层，这是你的加分项）

- **对照组（5 组）**：原朴素匹配 / BM25 / 向量 / 固定混合 / 自适应路由+纠错。
- **同一份 120 条标注集、同一套指标**，保证可比。
- **按查询类型分层报告**：点名型、症状型、别名型、多意图型、库外问题。
- **防泄漏**：评测问题不能照抄知识库原文；不能拿评测集调参。
- **误差分析**：把路由错判的案例归类（如"别名未收录""症状词不在词表""跨植物多意图"）。
- **可复现**：一条命令出表，随机性为零，日志落库。

### 2.6 用老师熟悉的"图书管理系统"做类比（汇报时直接用）

| 你的系统 | 图书管理系统里的对应物 |
|---|---|
| 植物 Plant | 书目（bibliographic record） |
| 知识片段 Chunk | 馆藏条目 / 章节 |
| BM25 倒排索引 | 书名/关键词索引 |
| 向量索引 | 主题/内容索引 |
| 别名/学名表 | 著者/统一题名 |
| 路由器 | 检索台的策略（按问题类型换检索方式） |
| 回退纠错 | 检索无结果时的二次检索/推荐 |
| 评测集 + eval.db | 读者提问样本 + 借阅/检索日志 |
| 缓存失效 | 书目更新后重建索引 |

**一句话**："我的检索层相当于给图书馆重设计了**索引体系 + 检索策略 + 检索日志**，而不是只换了一个查询函数。"

## 四、复试怎么讲（按时间版本）

> 前提：数字填你真实跑出来的；一句假话都别说。

### 4.1 30 秒版

> "我的毕设是一个植物养护问答系统：前端拍照识别植物，后端基于知识库生成养护建议。我做的核心工作，是把原来'按字面匹配'的检索**重新设计**成 BM25、向量、RRF 三路检索，加一个按问题特征选路的自适应路由器，以及检索质量不合格时的回退纠错。我建立了 120 条标注评测集和 5 组对照实验，结果表明在症状类和别名类查询上 Recall@5 提升了 ____，同时平均检索延迟下降了 ____ 毫秒。"

### 4.2 2 分钟版（加设计叙事）

在 30 秒版基础上补：
1. **为什么**：原实现要求用户用词与知识库正文一字不差，问"叶子发黄怎么办"搜不到"常见问题"，这是全系统唯一的痛点。
2. **怎么设计**：分层（输入/检索/决策/生成/评测）、数据模型（chunk 表 + 评测表 + 轨迹表）、接口契约（`retrieve` 签名扩展、下游不变）、路由决策表、回退规则。
3. **怎么验证**：5 组对照、按类型分层、误差分析（例如"别名未收录导致 BM25 失败，向量能救回 6/25 题"）。
4. **结论与局限**：知识库规模有限，结论是"趋势性"的；后续方向是学习型路由与重排。

### 4.3 5 分钟版（带图表）

建议准备 4 张图/表，按顺序讲：
1. 架构图（2.1）
2. 数据模型 / 表结构（2.2）
3. 路由决策表（2.4）
4. 实验对照表 + 分类型柱状图（2.5）

### 4.4 必答追问清单（背熟，每题 30 秒内答完）

| 追问 | 回答要点 |
|---|---|
| 数据这么小，结论可靠吗？ | 承认局限；样本外推要谨慎；用**分层指标 + 误差分析**说明趋势；报告库外问题的表现。 |
| 为什么不用纯向量？ | 植物名/学名/别名是**精确词**，生僻名和拉丁名向量表征弱；BM25 精确匹配强；两路错误**互补**（给你的证据）。 |
| 路由判错了怎么办？ | 回退纠错 + 误差分析；把高频错因归纳成规则改进，而不是拍脑袋。 |
| 这算 Agentic RAG 吗？ | **诚实**：目前是自适应检索路由（Adaptive-RAG 思路）+ 检索后纠错（CRAG 简化）。真正的 Agentic 需要多步工具调用与规划，是后续方向。 |
| 与 Adaptive-RAG 有何不同？ | 原作用训练的小分类器判断复杂度并决定检索次数；我用**可解释特征规则 + 检索质量回退**，面向中文植物领域，并自建本领域评测集。 |
| 怎么防 LLM 幻觉？ | RAG 提供证据 + prompt 约束基于资料 + 库外时给通用建议并提示；没有让模型自由发挥。 |
| 成本和延迟？ | 检索全本地、评测零 API；只有最终生成调一次 LLM；离线路线全程零 API。 |
| 为什么 RRF 用 k=60？ | 原论文经验值；k 平滑低排名影响；有条件可做敏感性实验。 |
| 为什么查询加 instruction、文档不加？ | Qwen3-Embedding 是 instruction-aware，查询侧加任务指令能对齐检索意图，文档侧保持裸文本。 |
| 你的贡献是什么？ | 设计并实现检索决策子系统 + 建立可复现评测协议 + 误差分析，而不是"调了几个库"。 |

### 5.4 体现"设计先行"的流程（老师最想听到的）

```
需求分析（用户怎么用、痛点是什么）
  → 概念设计（ER：植物/片段/查询/轨迹）
  → 逻辑设计（表结构、字段、主键外键）
  → 物理设计（文件分块、倒排、向量缓存、SQLite 日志、失效策略）
  → 接口设计（retrieve/router 契约）
  → 流程设计（输入→识别→路由→检索→回退→生成→展示）
  → 实验设计（对照组/指标/样本/防泄漏）
  → 实现与评测
```

强调：**先有设计文档，再有代码**；评测协议本身也是设计的一部分。

### 5.5 给老师看什么（顺序建议）

1. 先给 **1 页架构图 + 1 张表结构**
2. 再给 **路由决策表**
3. 最后给 **实验对照表 + 误差分析**
4. 演示：拍照→识别→追问→有据回答；再演示纯文字提问

### 5.6 老师可能追问的"设计"问题及答法

| 追问 | 答法 |
|---|---|
| 你的数据库设计在哪？ | 没有用 DBMS，但有等价设计：实体/主键/外键/索引/缓存失效；评测日志用 SQLite，可查询。 |
| 为什么不用现成向量数据库？ | 规模小（百级 chunk），本地矩阵即可；但保留了索引构建与缓存的完整设计，换 FAISS 只需替换 DenseIndex。 |
| 数据一致性怎么保证？ | 主数据（kb）与派生数据（chunks/向量）分离，内容哈希触发重建。 |
| 接口为什么这么设计？ | 下游无感、可单独评测、可回退；这是"可测试性"优先的设计。 |
| 怎么证明设计有效？ | 5 组对照 + 分层指标 + 误差分析 + 可复现日志。 |

## 六、论文 / 答辩结构建议

1. **绪论**：背景与意义；国内外研究（Adaptive-RAG/CRAG/Self-RAG）；研究内容与贡献
2. **相关技术**：BM25、向量检索、RRF、RAG 三代、路由与纠错
3. **需求分析**：功能需求（识别/问答/建议）；非功能需求（离线、成本、延迟、可评测）；用例
4. **系统设计**（重点章）：总体架构、数据设计（ER/表/物理/失效）、接口设计、路由与纠错设计、评测设计
5. **系统实现**：分块与索引、检索器、路由器、界面改造、评测脚本
6. **实验与结果**：数据集构建、对照组、指标定义、结果表、分类型分析、误差分析
7. **总结与展望**：贡献回顾；局限；Agentic RAG、学习型路由、重排

## 七、红线与坑

1. **数字必须真实**：没跑完就不写百分比；答辩被追问"怎么算的"要能现场解释公式。
2. **不硬吹 Agentic**：口径是"自适应检索路由 + 检索后纠错"。
3. **不贬低 CV**：它是输入端、是已完成工作量；"CV 过时"这种话说出口只会扣分。
4. **引用已核验**：本文档涉及的 9 篇文献已逐条核验（含 DOI / arXiv / CNKI 编号），完整清单、引用格式与核验方法见 `docs/参考文献.md`。注意中文那篇的 `F1=0.324` 与"综合正确率 96.9%"是**两个不同指标**，不能混着说；网上流传的"72%/65%/91%"查无出处，不要当自己的结果。
5. **评测集不能泄漏**：问题必须是改写后的真实问法，不能照抄知识库原文。
6. **别把"用了库"说成"发明算法"**：诚实描述"选型 + 组合 + 评测 + 误差分析"，这本身就是合格的本科研究。
7. **老师问"工作量"时**：用"5 组实验 + 120 条标注 + 数据设计 + 界面改造"回答，而不是"改了 51 行"。
